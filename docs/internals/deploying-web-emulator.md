# Deploying the web emulator

The editable source lives in `vsdk/web/`. The public site,
[ventilastation/website](https://github.com/ventilastation/website), has this
repo as its `vsdk/` submodule and publishes a copy of `web/` as its
`emulator/` directory. Treat that copy as build output: never edit it, and it
is not committed there either.

Three things the browser needs are generated, not committed:

- the sprite ROMs in `apps/micropython/roms/` (`tools/generate_roms.py`);
- `web/runtime-manifest.json`, the list of runtime files, and
  `web/runtime-bundle.json`, the Python, `meta.json` and ROMs the worker
  mounts as its filesystem (`tools/generate_web_runtime_bundle.py`);
- the `?v=` cache-busting versions in a published copy
  (`tools/stamp_web_versions.py`).

Nothing has to be regenerated by hand: each step below does it.

## While developing

The desktop emulator serves the web emulator at `http://localhost:5653/`
(the same server that answers OTA requests). Each time the page loads, the
server brings the ROMs, the manifest and the bundle up to date, rebuilding
only what changed (about 0.1 s when nothing did), and it makes the browser
revalidate every file. So edit, then reload the page: no `make` step, and no
`?v=` to bump. A ROM or bundle build that fails answers the page with a 500
and prints the traceback in the emulator's terminal.

`./vs-emu.sh` (or `emu.py` directly) also brings the ROMs up to date when it
starts, and an OTA push to the console rebuilds them before sending.

Serving `web/` from anything else (for example `python3 -m http.server`)
works too, but then run `make web-runtime-bundle` after changing Python,
`meta.json` or images.

## Deploying

A push to `main` deploys by itself:

1. CI runs on the push.
2. When it passes, `.github/workflows/deploy-website.yml` points the
   website's `vsdk` submodule at that commit and pushes the website. It
   never moves the website back to an older commit.
3. The website's Pages workflow (`.github/workflows/pages.yml` there) runs
   `make publish` from that checkout: it builds the ROMs and the bundle from
   scratch, copies `web/` and the asset trees into `emulator/`, stamps the
   `?v=` versions and builds the Jekyll site.

Step 2 needs a `WEBSITE_DEPLOY_TOKEN` repository secret in vsdk: a
fine-grained personal access token limited to `ventilastation/website` with
**Contents: Read and write**. Without it the workflow only reports that it
skipped, and the website keeps the vsdk commit it has; run the workflow
again from the Actions tab (*Deploy website → Run workflow*) once the secret
is set.

Stamping (in step 3) needs the website's `tools/update-emulator-from-vsdk.sh`
to call `python3 "$VSDK_DIR/tools/stamp_web_versions.py" "$OUT_DIR"` after
its copies. `stamp_web_versions.py` sets every `?v=` value, and the
`*_VERSION` constants that build `?v=` URLs at run time, to one hash of the
published files, so a changed module reaches every visitor on their next
load. It refuses to run on `web/` itself, and fails if a module builds a
`?v=` URL from a constant it doesn't know about.

### Building a published copy here

To inspect what will be published, or to publish by hand:

```sh
make web-emulator-bundle                     # builds dist/emulator
./tools/build-web-emulator-bundle.sh <dir>   # or into any directory
```

This rebuilds every ROM from scratch, then the manifest and bundle, copies
`web/` with real copies of `apps`, `games` and `system`, and stamps the
versions. It is not the website's exact layout: the website's own script
copies fewer files and adds what Jekyll needs.

## Rebuilding the MicroPython WASM runtime

Only needed when upgrading MicroPython itself or its build patches:

```sh
make micropython-webassembly
```

This clones pinned checkouts, applies the repo's patches, builds
`micropython.mjs`/`micropython.wasm` into `web/vendor/micropython/`, and
bumps the worker cache-busting version.

That target clones pinned `micropython` and `emsdk` checkouts into
`/tmp/vsdk-micropython-webassembly` by default and applies the repo's
trace-enabled WebAssembly variant and compatibility patch. Useful
overrides:

```sh
BUILD_ROOT=/tmp/custom-vsdk-build make micropython-webassembly
VERSION_TAG=20260618T160000Z make micropython-webassembly
BUILD_JOBS=8 make micropython-webassembly
```

## Post-deploy check

Load the published emulator, let the menu idle 30–60 s, and confirm
`Heap Used` stays steady (ARCHITECTURE.md, "Manual Regression Check").
